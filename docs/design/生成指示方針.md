**一度の指示につきファイルは 1 つ**で問題ありません。設計は後工程の入力になるので、まとめて 10 本出すより、1 本ごとに内容を固めた方がコーディング時の手戻りが少ないです。

例外はほぼなく、あるとすれば次だけです。

- **コード定義書（5）とテーブル定義書（6）**は依存が強いので、5 の直後に 6 を出す（別指示で連続）のがよいです。同じ指示で 2 ファイルにまとめる必要はありません。
- **同じチャットで、一覧の番号順**に出すのが最適です。チャットを分けるなら、毎回すでにできた `docs/design/*.md` を参照させてください。そうしないと用語やパスがずれます。

---

### 推奨の進め方

1. 同じ会話で、下のテンプレートの `N` と文書名だけ変えて 1 → 10 の順に依頼する。  
2. 各回の返信で「決めたこと／要件から変えたこと／コーディング前に見たい点」を確認する。ずれがあればそのファイルだけ直してから次へ。  
3. 10 まで終わったら、実装前に「設計書同士の矛盾チェック」を 1 回依頼する。  
4. コーディングは機能単位（例: 家計簿 CRUD）で、設計書を入力にする。

---

### 設計書作成用プロンプト（コピー用）

`N` と文書名を差し替えて使います。初回は `N = 1`、文書名は `システム構成設計書` です。

```markdown
@docs/requirements/要件定義書.md
@docs/design/設計成果物一覧.md
@docs/design/

【依頼】
設計成果物一覧の No.{N}「{文書名}」を、指定のファイル名で 1 ファイルだけ作成してください。
他の設計書・コード・DDL は作らないでください。

【入力】
- 要件の正は要件定義書とする。
- すでに docs/design にある設計書がある場合はそれに従い、矛盾する決め方をしない。
- 成果物一覧に「今回作らない」とある文書の範囲は書かない（他文書へ一文で委譲する）。

【粒度】
あとからこの設計書（と要件定義書）を入力にコーディングする。
そのため、方針の繰り返しではなく、実装者が迷わない決めを書くこと。
例: プロセス構成、URL/API パス、画面項目、ステータスコード、テーブル列と型、計算の手順、設定キー。
要件定義書の章のコピーや、未決定のままの「設計で定める」の持ち越しはしない。
判断が必要なら設計側で 1 つ選び、「設計判断:」と理由を短く残す。

【禁止】
- 要件にない機能の追加
- 公開 TLS、RDS、許可 IP リスト、時価自動取得など、対象外の復活
- この指示で複数ファイルを出力すること
```

2 本目以降は、必要なら次を 1 行足します。

```text
特に @docs/design/システム構成設計書.md のポート・パス・待受の決めに合わせること。
```

（実際に参照させるファイルは、その文書が依存するものだけにすると精度が上がります。一覧の 2.1 の矢印どおりです。）

---

### なぜこの形か

- `@` で正本を固定しないと、会話の要約だけで設計して要件とずれます。  
- 「1 ファイルだけ」を明示しないと、テーブル定義のついでに DDL や API まで書きがちです。  
- 「コーディングする」と書いておくと、図と文言だけでなくパス・型・計算手順まで落ちます。ここが後の実装品質に直結します。  
- 対象外の復活禁止は、IP 制限や公開 HTTPS が設計で戻ってくるのを防ぐためです。

### コーディング依頼時（先の話）

設計が揃ってから、機能単位で次のような指示が向いています。一度にリポジトリ全体を実装させるより、認証 → マスタ → 家計簿 → ダッシュボードの順が安全です。

```markdown
@docs/requirements/要件定義書.md
@docs/design/

【依頼】
{機能名} を、設計書どおり実装してください。
スキーマ・API パス・画面項目は設計書に合わせ、設計にない機能は足さないでください。
設計と実装が衝突する場合は、コードを書く前に差分を提示してください。
```

設計書作成に進めてよければ、上のテンプレートで No.1 から指示をもらえれば着手できます。
