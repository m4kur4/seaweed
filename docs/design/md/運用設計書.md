# seaweed 運用設計書

No.10 ／ 版 1.0 ／ 2026-08-30 ／ 入力: 要件定義書 1.3、システム構成設計書 1.0、認証セキュリティ設計書 1.0、インフラ設計書 1.0

起動停止、設定変更、推奨バックアップ、障害の切り分けを固定する。担当は利用者自身。SLA・死活監視・アラートは設けない（要件 6.5）。RPO / RTO は定めない（OPS-BAK-03）。

待受・パス・env キーはシステム構成。SG・インスタンスはインフラ。ハッシュ方式は認証セキュリティ。テーブル DDL はテーブル定義書。本書類は **操作手順** を正とする。

## 1. 方針

| 項目 | 決め |
| --- | --- |
| 運用者 | 利用者 1 名。AWS コンソールと SSH（`ec2-user`）と Tailscale 管理画面 |
| 気づき | ブラウザで `http://seaweed/` が使えないこと。外部監視は置かない |
| 停止の受容 | パッチ・再起動・デプロイ中は使えない（R-08）。告知の仕組みは作らない |
| 秘密 | `/etc/seaweed/seaweed.env` のみ。Git・チャット・スクリーンショットに平文とハッシュを残さない |

切り分けの層は常にこの順: **端末 Tailscale → インスタンス生存 → SSH → Serve / アプリ health → mysqld**。

## 2. systemd ユニット

パス: `/etc/systemd/system/seaweed.service`。秘密なし。リポジトリに同じ内容の雛形を置いてよい（本依頼では作らない）。

```ini
[Unit]
Description=seaweed
After=network-online.target mysqld.service
Wants=mysqld.service

[Service]
Type=simple
User=seaweed
Group=seaweed
WorkingDirectory=/opt/seaweed
EnvironmentFile=/etc/seaweed/seaweed.env
Environment=JAVA_TOOL_OPTIONS=-Duser.timezone=Asia/Tokyo -Xms256m -Xmx512m
ExecStart=/usr/bin/java -jar /opt/seaweed/seaweed.jar
SuccessExitStatus=143
TimeoutStopSec=30
Restart=on-failure
RestartSec=5
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

- `SuccessExitStatus=143` は SIGTERM 時の JVM 終了コード。stop を failed に見せない。
- ヒープと TZ はユニットの `Environment=`。ハッシュは **EnvironmentFile だけ**（`$2a$...` を `Environment=` に書くと systemd が展開する）。
- 変更後は `sudo systemctl daemon-reload`。

boot 時に上げるサービス: `seaweed`、`mysqld`、`tailscaled`、`sshd`（sshd はパッケージ既定で enable）。

```text
sudo systemctl enable seaweed mysqld tailscaled
```

## 3. 環境変数ファイル

パス: `/etc/seaweed/seaweed.env`。権限 **640**、所有者 **root:seaweed**。Git に含めない。

```text
SPRING_PROFILES_ACTIVE=prod
SERVER_ADDRESS=127.0.0.1
SERVER_PORT=8080
SPRING_DATASOURCE_URL=jdbc:mysql://127.0.0.1:3306/seaweed?characterEncoding=UTF-8&connectionTimeZone=Asia/Tokyo
SPRING_DATASOURCE_USERNAME=seaweed
SPRING_DATASOURCE_PASSWORD=<DBパスワード>
SEAWEED_AUTH_USERNAME=<ログイン名>
SEAWEED_AUTH_PASSWORD_HASH=<BCrypt文字列全体>
```

キー名はシステム構成 7 章から増やさない。値に空白を入れない。ハッシュは引用符なし 1 行、`$` をエスケープしない。末尾改行は付ける。

作成・権限:

```text
sudo install -d -m 755 /etc/seaweed
sudo install -m 640 -o root -g seaweed /dev/null /etc/seaweed/seaweed.env
sudoedit /etc/seaweed/seaweed.env
sudo chown root:seaweed /etc/seaweed/seaweed.env
sudo chmod 640 /etc/seaweed/seaweed.env
```

編集は `sudoedit /etc/seaweed/seaweed.env`。反映は **必ず** `sudo systemctl restart seaweed`。env はプロセス起動時だけ読む。

## 4. 起動・停止・再起動

SSH 先はインフラの Elastic IP。ユーザ `ec2-user`。作業はすべてホスト上。

| 目的 | コマンド |
| --- | --- |
| アプリ状態 | `sudo systemctl status seaweed` |
| 起動 | `sudo systemctl start seaweed` |
| 停止 | `sudo systemctl stop seaweed` |
| 再起動 | `sudo systemctl restart seaweed` |
| MySQL | 同様に `mysqld` |
| Tailscale | `sudo systemctl status tailscaled` |

**止める順:** `seaweed` →（DB メンテするときだけ）`mysqld`。sshd と tailscaled はメンテ中も止めない。

**起動順:** `mysqld` が active であること → `seaweed`。mysqld を再起動したあとは `seaweed` も restart する（接続プールが死んでいるため）。

再起動すると **全セッション無効**（メモリセッション。認証セキュリティ）。利用者は再ログインする。

ホスト上の生存確認（認証不要）:

```text
curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/api/v1/health
```

期待は `200` と本文 `{"status":"ok"}`。これが失敗ならブラウザの話の前にアプリを疑う。

EC2 インスタンスそのものの停止・起動は AWS コンソール。EIP は付いたまま。OS 再起動後に `seaweed` / `mysqld` / `tailscaled` が active か、`tailscale serve status` が HTTP 80 かを確認する。

## 5. デプロイ（JAR 入れ替え）

ビルドは開発機（システム構成 5.1）。本番に Node / Maven は入れない。

```text
# 開発機
scp -i <秘密鍵> backend/target/seaweed.jar ec2-user@<EIP>:/tmp/seaweed.jar

# EC2
sudo systemctl stop seaweed
sudo cp -a /opt/seaweed/seaweed.jar /opt/seaweed/seaweed.jar.bak
sudo mv /tmp/seaweed.jar /opt/seaweed/seaweed.jar
sudo chown seaweed:seaweed /opt/seaweed/seaweed.jar
sudo chmod 644 /opt/seaweed/seaweed.jar
sudo systemctl start seaweed
curl -sS http://127.0.0.1:8080/api/v1/health
```

失敗したら `seaweed.jar.bak` を戻して start。スキーマ変更が含まれるリリースは、**アプリ停止中**にテーブル定義書の SQL を手適用してから start。Flyway は使わない。

## 6. 認証情報の変更

画面・API はない（OPS-RUN-03）。ログイン中セッションは restart で切れる。

**ハッシュ生成は開発機。** 平文を EC2 のシェル履歴に残さない。BCrypt 強度 **12**（認証セキュリティ）。

```text
python3 - <<'PY'
import bcrypt, getpass
pw = getpass.getpass("plain: ").encode("utf-8")
print(bcrypt.hashpw(pw, bcrypt.gensalt(rounds=12)).decode())
PY
```

`bcrypt` が無いときは開発機で `BCryptPasswordEncoder(12).encode(...)`（認証セキュリティ 4 章）。出力が `$2a$12$` / `$2b$12$` / `$2y$12$` で始まることを確認する。ダミーハッシュ定数は本番に使わない。

1. `sudoedit /etc/seaweed/seaweed.env` で `SEAWEED_AUTH_USERNAME` および／または `SEAWEED_AUTH_PASSWORD_HASH` を差し替え。
2. `sudo systemctl restart seaweed`
3. `systemctl is-active seaweed` が `active`。起動失敗なら journal（ハッシュ形式不正・`changeme`・空）。
4. `http://seaweed/login` で新資格情報を確認。

平文パスワードは生成後にメモから消す。env にはハッシュだけ残す。

## 7. DB パスワードの変更

アプリを先に止める。`'seaweed'@'127.0.0.1'` のみ（インフラ 8 章）。

```text
sudo systemctl stop seaweed
sudo mysql -e "ALTER USER 'seaweed'@'127.0.0.1' IDENTIFIED BY '新しい平文'; FLUSH PRIVILEGES;"
sudoedit /etc/seaweed/seaweed.env   # SPRING_DATASOURCE_PASSWORD
sudo systemctl start seaweed
curl -sS http://127.0.0.1:8080/api/v1/health
```

root はソケット（`sudo mysql`）。アプリに管理者パスワードを持たせない。

## 8. SSH 用 SG の更新

自宅グローバル IPv4 が変わって SSH できないとき（OPS-RUN-06）。アプリのログインとは無関係。

1. いまの回線から IPv4 を確認する: `curl -4 -sS https://checkip.amazonaws.com`
2. AWS コンソール（`ap-northeast-1`）→ EC2 → セキュリティグループ `seaweed-prod` → インバウンドの編集。
3. TCP **22** のソースを新しい `/32` にする。古い /32 は削除。
4. **22 を 0.0.0.0/0 にしない。** 80 / 443 / 8080 / 3306 を足さない。
5. Elastic IP に対し `ssh -i <鍵> ec2-user@<EIP>`。

コンソールに入れること（NFR-SEC-06）。Tailscale が死んでいてもこの経路は残す。

## 9. Tailscale

| 作業 | 手順 |
| --- | --- |
| 端末追加 | 端末に公式クライアント。同じ tailnet にログイン。MagicDNS オン。`http://seaweed/`（http。https ではない） |
| 端末除外 | Tailscale 管理画面でデバイスを削除。ISP の IP 変動では何もしない（OPS-RUN-02） |
| Serve 確認 | EC2 で `tailscale serve status`。HTTP 80 → `http://127.0.0.1:8080`。443 や Funnel があれば `sudo tailscale serve reset` のあと `sudo tailscale serve --bg --http=80 http://127.0.0.1:8080` |
| ノード名 | `tailscale set --hostname=seaweed` |
| OS 再起動後 | `tailscaled` が active なら Serve 設定は残る。消えていたら上の Serve コマンドを再実行 |

Funnel は使わない。無効化の確認は `tailscale status` と管理画面。

## 10. ログとディスク

アプリログは STDOUT → journald（システム構成）。ファイルには落さない。

| 目的 | コマンド |
| --- | --- |
| アプリ直近 | `sudo journalctl -u seaweed -n 200 --no-pager` |
| 追跡 | `sudo journalctl -u seaweed -f` |
| MySQL | `sudo tail -n 200 /var/log/mysqld.log` |
| ディスク | `df -h /` |
| メモリ | `free -h` |

パスワード・ハッシュを journal に出さない（認証セキュリティ 9 章）。5xx の本文は「サーバエラーです」。詳細は journal だけ。

`/` が逼迫したら `sudo journalctl --vacuum-size=80M`。MySQL データは `/var/lib/mysql`。30 GiB を使い切る想定は個人データでは稀。VACUUM してもスナップショットの代替にはしない。

## 11. OS・MySQL のパッチ

`dnf-automatic` は入れない（インフラ）。利用者が日時を選んで止める。

```text
sudo systemctl stop seaweed
sudo dnf update -y
# カーネルが出たら reboot。出なければ mysqld が生きていることを確認して seaweed start
sudo reboot
# 復帰後
sudo systemctl is-active mysqld seaweed tailscaled
curl -sS http://127.0.0.1:8080/api/v1/health
sudo tailscale serve status
```

MySQL のメジャー更新はスナップショットを取ってから。8.4 のままパッチする。MariaDB への乗り換えはしない。

## 12. 推奨バックアップ

Must ではない（OPS-BAK-01）。インスタンス terminate・ディスク故障ではデータ全損になりうる（R-03）。

**正本:** AWS 上の **EBS スナップショット**（インスタンスの外）。同一ディスク上の dump だけに頼らない。S3 は使わない（IAM ロールなし。インフラ D-INF-10）。

| 項目 | 決め |
| --- | --- |
| 対象 | ルートボリューム 1 本（インフラ。`/opt` と `/var/lib/mysql` を含む） |
| 頻度 | 週 1 回を目安。家計を大きく入れた直後も可 |
| 手順 | コンソール EC2 → Elastic Block Store → Volumes → インスタンス `seaweed` のルート → Create snapshot。名前 `seaweed-YYYY-MM-DD` |
| 世代 | 直近 **4** 件を残し、古いものは手で削除 |
| アプリ停止 | 必須にしない（個人・クラッシュコンシステントで足りる）。厳密にするなら snapshot 直前に `stop seaweed` と `sudo mysqladmin flush-tables with read lock` だが、通常は省略してよい |
| cron | 置かない（IAM が無いのでインスタンスから snapshot API を呼ばない） |

`mysqldump` は任意の論理コピー。同じ EBS に置くとインスタンス喪失で一緒に消える。取るなら開発機へ `scp` してから EC2 上のファイルを消す。

```text
sudo systemctl stop seaweed
mysqldump -h 127.0.0.1 -u seaweed -p --single-transaction seaweed > /tmp/seaweed-$(date +%F).sql
sudo systemctl start seaweed
# 開発機へ scp したあと EC2 の /tmp から削除
```

## 13. リストア

RTO は定めない。作業中は使えない。

### 13.1 EBS スナップショットから（推奨）

同一 AZ。EIP と SG `seaweed-prod` は付けたまま。

1. インスタンスを **Stop**。
2. ルートボリュームをデタッチ。名前を控える。
3. スナップショットからボリュームを作成（同じ AZ、gp3、暗号化オン）。
4. 新ボリュームをルートとしてアタッチ（Nitro ではデバイス名 `/dev/xvda`）。
5. インスタンスを **Start**。EIP が戻ること、SSH、health、`http://seaweed/` を確認。
6. 旧ボリュームは確認後に削除。

スナップショットから AMI を作って別インスタンスを起動してもよい。その場合は EIP を付け替え、SG を `seaweed-prod` にする。ホスト名と `tailscale up` と Serve をインフラ 7・10 章どおりやり直す。

### 13.2 mysqldump から

アプリ停止。既存データは上書きされる。

```text
sudo systemctl stop seaweed
mysql -h 127.0.0.1 -u seaweed -p seaweed < seaweed-YYYY-MM-DD.sql
sudo systemctl start seaweed
```

テーブル定義が dump 時点と違う JAR を載せることはしない。スキーマを変えたリリースは dump もその版で取り直す。

## 14. 障害時の切り分け

監視はない。次を上から実行する。

```mermaid
flowchart TD
  A[http://seaweed/ が使えない] --> B{端末 Tailscale 接続と MagicDNS}
  B -->|切れている| B1[端末で Tailscale を接続]
  B -->|OK| C{AWS コンソールでインスタンス running}
  C -->|stopped / terminated| C1[Start。terminated ならリストア]
  C -->|running| D{SSH できるか}
  D -->|否| D1[8 章: SG の 22 を今の /32 に]
  D -->|可| E{"curl health が 200 か"}
  E -->|否| F{systemctl is-active seaweed mysqld}
  F -->|mysqld 死| F1[journal と mysqld.log。start mysqld のち seaweed]
  F -->|seaweed 死| F2[journalctl -u seaweed。env・ハッシュ・OOM]
  F -->|両方 live| G[listen を確認: ss -lntp | grep 8080]
  E -->|200| H{tailscale serve status が HTTP 80}
  H -->|なし / HTTPS / Funnel| H1[9 章の Serve やり直し]
  H -->|OK| I[端末 DNS が 100.x か。ブラウザは http]
```

| 症状 | 見る場所 | よくある原因 |
| --- | --- | --- |
| 画面そのものが出ない | 上図 B〜H | 端末 Tailscale、Serve、インスタンス停止 |
| ログイン画面は出るが 401 | アプリは生きている | 資格情報。6 章。ロックは無い |
| ログイン後 5xx | `journalctl -u seaweed` | DB 接続。mysqld、パスワード不一致 |
| health は 200 だが業務が 500 | journal、mysqld | テーブル未適用、ディスク満杯 |
| SSH だけできない | SG 22 | 自宅 IP 変動。8 章。コンソールは別経路 |
| パブリック EIP:80 に繋がる | SG の誤り | 80 を開けていたら削除。アプリは localhost のみが正 |

OOM: `dmesg` に kill。ヒープはユニットどおり 512m。続くならインフラのとおり t4g.medium。

`GET /api/v1/health` は DB を見ない。health 200 でも mysqld 死では業務 API が 500 になる。切り分けのために health と `systemctl is-active mysqld` を両方見る。

## 18. 設計判断一覧

| ID | 判断 | 理由 |
| --- | --- | --- |
| D-OPS-01 | ログは journald のみ | ファイルとローテーションを増やさない。要件は参照できればよい |
| D-OPS-02 | バックアップの正は手作業の EBS スナップショット週 1、世代 4 | インスタンス外に残る。IAM/S3/cron を足さない |
| D-OPS-03 | dump は任意。同じディスクだけに置かない | terminate で同時喪失するため |
| D-OPS-04 | ハッシュ生成は開発機。EC2 の履歴に平文を残さない | OPS-RUN-03 と認証セキュリティ |
| D-OPS-05 | ハッシュは EnvironmentFile にだけ書く | systemd の `Environment=` が `$` を展開するため |
| D-OPS-06 | 監視を置かない | 要件 6.5。切り分けは 14 章の手作業 |
| D-OPS-07 | デプロイは scp + 停止入れ替え | 本番にビルドツールを置かない（インフラ） |
| D-OPS-08 | SIGTERM を 143 で成功扱い | stop が failed に見えるのを防ぐ |
